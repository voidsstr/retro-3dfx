# 09 — Incomplete, Absent & Anomalous Areas

An honest accounting of what is *not* here, what was left unfinished when 3dfx shut down, and
what to watch out for. Ordered by impact on your project.

## 1. No Windows XP driver exists — anywhere in this tree

- The newest Windows target is **Windows 2000** (`H5/W2K`). XP shipped October 2001, after
  3dfx's demise; 3dfx never wrote an XP driver.
- The W2K driver is the direct ancestor of every community XP driver (Amigamerlin 3.x, SFFT,
  x3dfx): XP's display-driver model (XPDM) is an evolution of W2K's, so the W2K
  miniport+display pair generally loads on XP with INF edits — that is exactly what the
  community shipped. Evidence of late W2K hardening is in the source: NT5 kernel-PTE
  exhaustion workaround (`W2K/.../Miniport/H5/H3.C:1775`), "Must be NULL for NT5!"
  (`H3.C:249`), `#if (_WIN32_WINNT < 0x0500)` guards in `BUILD/STBPERF.INC`.
- **Implication for Phase 1**: "build as-is" gives you 98SE/W2K targets. An XP target =
  W2K tree + INF changes + testing; a Vista+/WDDM or modern-Windows target is a rewrite.

## 2. NT4 display driver has no Direct3D

`H5/WinNT/Src/Video/Displays/H5` (86 files) contains 2D/DirectDraw/escape support only —
no `D3*/D6*` sources (compare W2K's 152 files which include the full D3D HAL). D3D games on
NT4 were never supported; Glide and OpenGL-over-Glide were the NT4 3D paths. Not a defect —
a deliberate scope decision of the era — but document-worthy if you plan an NT4 build.

## 3. DX8 support is a stub

`H5/Win9x/DX/D3D/D8DP2.C` (946 lines) handles the DX8 DDI entry/negotiation but the driver
reports and implements DX6/DX7-class capabilities (no pixel/vertex shaders — the hardware
has none). DX8 titles ran through the DX7 HAL path. Treat `D8DP2.C` as scaffolding, not a
feature.

## 4. Absent sibling hardware trees

Top-level `MAKEFILE` selects `FX_GLIDE_HW` ∈ {SST1, SST96, CVG, H3, H5} and would recurse
into `sst1/`, `cvg/`, `h3/` — **none of those directories exist in this snapshot**. Voodoo1/
Rush/Voodoo2 Glide cannot be built from here, and the standalone H3 (Banshee) Glide tree is
absent. Not needed for V3/V5: the H5 trees' runtime device checks (`IS_NAPALM`, device-ID
switches) cover Avenger and Napalm boards, and the OS drivers ship Voodoo3 INFs.

## 5. Mac Napalm support was alpha

`H5/MacOS8/release_notes/napalm_alpha/`, `BuildScripts/delivrable_specs/napalm_alpha` — the
Mac Voodoo4/5 stack shipped only in alpha before the shutdown (retail Mac Voodoo4/5 cards
never launched). Voodoo3 Mac support (`voodoo3_beta` specs) reached beta. One Mac source file
is empty in this archive (below). Expect rough edges throughout `MacOS8/`.

## 7. Archive provenance & anomalies

- `diags.diff` / `diags_done.diff` are **not diffs** — they are saved MKS-grep search logs
  referencing `D:\OfficialBuild\AAlchemy3\MfgTests\src\...`. This snapshot came off a
  **Quantum3D** build machine (AAlchemy was Q3D's multi-VSA-100 arcade/sim platform), which
  also explains the `Q3d*.cmd` env scripts, `QMODES.H` Quantum3D video modes,
  `FX_GLIDE_PERFORMANCE_TRILINEAR_Q3D`, and the Lua test-client mentions of Q3D
  authentication hardware in `MFTG`.
- Directory timestamps run to **Jan 9 2002** (files to Nov 13 2000) — the tree was touched/
  repackaged after 3dfx's asset sale closed (Dec 2000–Apr 2001), consistent with Quantum3D's
  licensed continued use.
- `H5/NICKTEST/` — an engineer's private header snapshot + makefile; no unique code.
- `H5/cinit-old/` — superseded CINIT kept for reference; do not build.
- `SWLIBS/3DfxSplashOld/` vs `3DfxSplash/` vs `NuSplash/` — three generations of the splash
  screen; only NuSplash matters for Napalm-era Glide.
- `SWLIBS/OPENGL` contains **three** generations of the GL driver (SRC → GLIDE2X → GLIDE3X);
  only GLIDE3X targets this hardware generation cleanly.
- Checked-in build outputs (`.OBJ`, `.LIB`, `.EXE`, `.COD`, `RETAIL/DEBUG` dirs) are from the
  original 2000 builds — handy as reference binaries/disassembly but will be overwritten.

## 8. Known-incomplete engineering threads (from changelogs/comments)

- **Alt-tab / desktop corruption** in windowed Glide was still being chased
  (`FIFO.C` rev 30: works "with DEBUG glide only. In the non-debug glide, we can still see
  the desktop corruption"; `GLIDE_ALT_TAB` build flag).
- **NT mutexing** between DDraw and ExtEscape paths flagged as unresolved
  (`FIFO.C` 12/98 note) — multi-window NT Glide is fragile.
- **K7 3DNow! disabled** as a "temp workaround" (`GPCI.C` changelog: "Remove 3DNow for K7") —
  Athlon took the default x87 path in Glide3 at snapshot time.
- **4-way SLI (Voodoo5 6000)** support is present but was never productized; the analog-SLI
  forcing and quad paths (`DDFXS32.C` QUAD_CHIP_* configs) got limited real-world testing.
  If you own only a 5500, the 2-chip paths are the hardened ones.
- **AGP command FIFO on Voodoo3** deliberately disabled (hardware bug; `DDFXS32.C` comment) —
  do not re-enable on V3 in Phase 2.
- **8x FSAA** plumbing exists (`dwaaSampleHigh==2`) but requires 4 chips; on a 5500 the real
  modes are 2x/4x.
- `FX_CHRIS_DENIS_ANTHONY_HACK` build flag in `makefile.linux` — an undocumented Linux
  experiment left in the build system; off by default, leave it off.
- The Glide3 `xdraw3_3dnow.obj`-era assembly predates several C-path fixes noted in
  changelogs ("Hack to allow defferent SETF macro to be used", GAA.C) — when C and ASM paths
  disagree, trust the C path and re-derive.

## 9. What you'd have to source externally

- The four DDKs/SDKs and MSVC 6/1.52/MASM 6.14 toolchain (abandonware archives).
- Rampage (next-gen) material: only a marketing PPT is here (`Rampage_Q3D_083199.ppt`) —
  no Rampage code exists in this tree.
- No standalone `.doc→text` conversions: the authoritative chip docs are the binary Office
  files + `DATABOOK.PDF` in `H5/DOCS` (readable as-is).
