# Deploying this repo's stack to the Voodoo 5 6000 on `.191`, 2026-09-04

Task: the "Strange God" Voodoo 5 6000 moved to a new box. Deploy this repo's
drivers, get the games onto the right OpenGL/Glide, and benchmark against the
last numbers taken on the old Pentium III machine.

## 1. The card moved, and nothing in the repo knew where

`V56K-PLAN.md`, `V56K-SLI-FINDINGS.md`, `bench-safe.py`, `bench-ut.py` and the
build README all say the Voodoo 5 6000 is in **`.133` "P3-DUAL"**. It is not, and
has not been since 2026-08-31. `docs/fleet-inventory.md` in the sibling repo had
already recorded the card leaving `.133` (GeForce4 Ti 4600 there now) but no
record placed it anywhere else.

**It is in `192.168.1.191`** — a box in no roster and no inventory:

| | |
|---|---|
| Hostname | `NSC-AF6CF7A80BC` |
| CPU | AMD Athlon, 1152 MHz, family 6 model 10 (single socket) |
| RAM | 511 MB |
| Chipset | nVidia **nForce2** (`10DE:0060` ISA bridge, `10DE:01E0` AGP/mem) |
| OS | Windows XP SP3 |
| Card HWID | `PCI\VEN_121A&DEV_0009&SUBSYS_0001121A&REV_01` |
| Bridge | `PCI\VEN_3388&DEV_0021` — HiNT HB1-SE66, **the decisive 4-chip marker** |

The find method that works, and the only one that should be trusted: sweep the
subnet for port 9898, then ask each agent `VIDEODIAG` + `REGREAD ...\Enum\PCI`.
Two live boxes turned up that appear in no roster (`.186`, `.191`). Everything
else on the fleet was powered off.

> **`SUBSYS_0001121A` closes a `V56K-PLAN.md` Phase-1 item.** The plan lists
> "exact 6000 subsystem HWID in `voodoo5-6k.inf`" as open. The card reports
> `SUBSYS_0001121A`, and the deployed INF already carries that exact row. The
> repo's own `toolchain-3dfx/dist/.../voodoo5-6k.inf` is STALE by comparison —
> see §5.

## 2. It was running the stock 2001 driver, with no Glide and no ICD at all

Before anything was deployed:

```
system32\3dfxvs.dll            689,216   17/08/2001   <- stock 3dfx reference display driver
system32\drivers\3dfxvsm.sys   148,352   17/08/2001   <- stock reference miniport
system32\glide2x.dll           ABSENT
system32\glide3x.dll           ABSENT
system32\3dfxogl.dll           ABSENT
HKLM\...\OpenGLdrivers         EMPTY (no ICD registered)
```

Class key: `InfPath=3dfxvs2k.inf`, `DriverVersion=5.1.2001.0`,
`ProviderName=Microsoft`.

So on arrival this box could not run Glide **at all**, and every OpenGL title was
falling back to Microsoft's software renderer. Any "the Voodoo is slow" impression
from before this date is that, not the card.

## 3. Activation had to be fixed before the reboot, not after

`PROCLIST` showed **`wpabaln.exe` running** — the XP activation nag. This is the
exact precondition that cost `.171` a day on 2026-08-29 (CLAUDE.md, "CHECK
ACTIVATION BEFORE YOU REBOOT A BOX"): an unactivated box is fine while logged in
and unreachable the moment it restarts. `scripts/fleet/safe-reboot.py` refuses to
reboot a box in this state, and correctly so.

The wizard reported **60 days of grace left**, so the reboot was not yet fatal —
but it was resolved anyway, because the nag also runs at every logon and steals
CPU from benchmarks.

**Activated fully remotely, no keyboard at the machine**, which the
`xp-activation` skill documents as needing a person at the screen. The agent's UI
automation is enough:

1. `LAUNCH %systemroot%\system32\oobe\msoobe.exe /a`
2. `UICLICK` the "telephone a customer service representative" radio → Next
3. `SCREENSHOT 0`, crop and magnify the Step-3 line, read the 54-digit
   Installation ID
4. `xpcid <installation-id>` on the dev host → Confirmation ID (its per-group
   check digits validating is itself proof the ID was read correctly)
5. `UICLICK` field A, `UIKEY TEXT:<42 digits>` — the wizard auto-advances A→G
6. Next → **"Thank You!"**, then `msoobe /a` again → "Windows is already
   activated."

`safe-reboot.py`'s activation gate went from refusing the box to
`activation ok` on the strength of that.

## 4. What was deployed

**Not a fresh build.** The Wine/VC6/DDK build tree is absent on this host
(`toolchain-3dfx/wine` does not exist, and commit `850620f` untracked the
prefix tree), so `tests/predeploy.sh` cannot gate an artifact it cannot see —
its 33 failures are all "repo tree != build tree" and "DLL not found" against a
tree that is not there. The 56 repo-tree source assertions all PASS, and
`tests/run_native.sh` is fully green.

What was deployed instead is the **md5-pinned, hardware-verified snapshot that
produced the `.133` baselines** — `optimized/deployed-133-v56k-20260811/`. That
is the right choice for a like-for-like comparison: the only variable between the
old numbers and the new ones is the host machine.

### The install

`updrv.exe` (the older helper) fails here with
`0x00000005 ERROR_ACCESS_DENIED: must run as Administrator` **even though the
agent runs as Administrator** — a misleading message; the tool is simply wrong.
`tools/drvupd.c` built fresh with mingw works first time:

```
rescan: ok (0x0)
INSTALLED PCI\VEN_121A&DEV_0009&SUBSYS_0001121A via ...\voodoo5-6k.inf (reboot needed)
```

Prerequisites that matter: driver-signing policy silenced
(`HKLM\Software\Microsoft\Driver Signing` `Policy`=REG_BINARY `00`) and
`Control\Windows` `ErrorMode`=2, or the headless EXEC blocks on an invisible
dialog. Full registry rollback exported first to
`C:\RETRO_AGENT\v56k-rollback\`.

Reboot via `scripts/fleet/safe-reboot.py` (arms the PXE hold first — the PXE
server **is** running, and a plain REBOOT risks the box re-imaging itself). Box
came back in **146 s**.

```

  DriverDesc    = 3dfx Voodoo5 6000

Device0\Glide    SSTH3_SLI_AA_CONFIGURATION = 5, FX_GLIDE_ANALOG_SLI = 1
OpenGLdrivers\3dfx  DLL = 3dfxogl.dll
```

Driver flight-recorder ring on first boot:

```
DDRAW-ENABLED: units=4 cyMem=4095 slop=5 ddHeap=3298
PRIMARY-TILED: scrOff=81E80000h 1024x768x16
DDGDDI-OK: d3dGlobal=... heaps=9
```

**`units=4`** — all four VSA-100s, 9-heap SLI layout, same as `.133`.
Quake III loads the ICD: `GL_RENDERER: 3Dfx [retro3dfx 0.5.0]`.

One difference from `.133` worth recording: this card is in **128 MB VBIOS mode**
(`HardwareInformation.MemorySize = 0x08000000` = 128 MB total = **32 MB/chip**).
The `.133` baselines were taken in 256 MB mode (64 MB/chip). Per
`V56K-SLI-FINDINGS.md` §12 that costs no frame rate on these workloads (they are
not fill- or memory-bound), only texture headroom.

## 5. `toolchain-3dfx/dist/.../voodoo5-6k.inf` in the repo is STALE

The INF that was actually deployed and verified on `.133` (`oem15.inf`, kept in
`optimized/deployed-133-v56k-20260811/`) is **strictly better** than the one the
repo ships, and the difference is all 6000-specific:

| | repo `voodoo5-6k.inf` | deployed `oem15.inf` |
|---|---|---|
| `SUBSYS_0001121A` maps to | `3dfxvsV5` (5500 defaults) | **`3dfxvsV6`** |
| `[3dfxvsV6]` section | absent | present |
| `MaximumDeviceMemoryConfiguration` | 132 | **260** |
| `SSTH3_SLI_AA_CONFIGURATION` | 2 (2-way) | **5 (4-way)** |
| `FX_GLIDE_ANALOG_SLI` | — | **1** |

Installing the repo's copy on this card would have silently configured it as a
**2-way 5500**. The deployed INF is the one to keep.

## 6. Game driver audit

`system32` now holds the right Glide and the ICD is registered, so the fleet's
OpenGL and Glide titles resolve correctly. Two game directories were shadowing
system32 with **nGlide** (Zeus Software) — a Glide→Direct3D *wrapper*, staged
2026-08-27 when this box had no Glide runtime at all:

```
C:\Games\Carmageddon2\glide.dll / glide2x.dll / glide3x.dll   (1.29-1.33 MB each)
C:\Games\UnrealGold\System\glide2x.dll                        (1.31 MB)
```

On real 3dfx silicon a Glide wrapper is precisely the wrong driver — it
translates Glide to D3D and back through our own D3D HAL, the slowest path on the
card, instead of talking to the hardware natively. All four renamed to
`*.nglide-wrapper-bak` (reversible). `GlideDrv.dll` in the Unreal trees is an
Unreal *render device*, not a Glide runtime, and was correctly left alone.
