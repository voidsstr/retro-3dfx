# Deploying this repo's stack to the Voodoo 5 5500 (.143), 2026-08-14

Task: deploy the drivers to `.143` and test. Done — with one large discovery that
reframes every benchmark taken on that box today.

## 1. The headline: `.143` was never running this repo's kernel driver

The active display driver on `.143` is **AmigaMerlin 3.1-R11**, not ours:

```
Class\{4D36E968-...}\0001
  DriverDesc    = AMIGAMERLIN 3.1-R11 For Voodoo 5 5500 AGP
  ProviderName  = 3dfx Interactive, Inc.
  DriverVersion = 5.1.2605.5
Services\3dfxvs  ImagePath = system32\DRIVERS\3dfxv5r.sys
```

And decisively — a registry-wide search for the display driver this repo builds:

```
reg query HKLM\SYSTEM\CurrentControlSet /s /f 3dfxv5d   ->  NOT REFERENCED ANYWHERE
```

`3dfxv5m` is not a service at all. So **both kernel-mode files this repo ships
(`3dfxv5d.dll`, `3dfxv5m.sys`) are inert on that box** — they sit on disk and
nothing loads them. The loaded miniport is AmigaMerlin's `3dfxv5r.sys`.

**Consequence for today's earlier findings:** every `.143` number in
`OPEN-STACK-ON-VSA100.md` — the 159.5 fps vintage baseline, the 93.5 fps Mesa 6.3
result, and both open-stack failures — was measured on **AmigaMerlin's kernel
display driver**, not ours. The ICD/Glide comparisons between those rows remain
valid (they varied only user-mode layers on a fixed kernel), but none of them is a
measurement of this repo's *driver*. The `.143` stack was AmigaMerlin kernel +
mixed user-mode.

This also means `CLAUDE.md`'s rule — *"the Voodoo 5 box runs THIS repo's drivers
ONLY"* — has been violated at the kernel level on `.143`, and file-copy deployment
cannot fix it: the binding is by **service + INF/PnP registration**, not filename.

## 2. What was deployed, and what actually took effect

Gate: `tests/predeploy.sh` **112 PASS / 0 FAIL, exit 0** before deploying.
Full recovery backup of all six binaries pulled first; every original moved aside
to `*.predeploy.bak` on the box rather than overwritten.

| File | Deployed | Effect |
|---|---|---|
| `glide2x.dll` | 258,048 B (ours, was 94,208 foreign) | ✅ **ACTIVE** — games load it directly |
| `glide3x.dll` | 339,968 B (ours, was 344,064 retail) | ✅ **ACTIVE** |
| `3dfxogl.dll` | 708,608 B `retro3dfx 0.5.0` (was Mesa 6.3, 2,646,009) | ✅ **ACTIVE** |
| `opengl32.dll` | 708,608 B `retro3dfx 0.5.0` (was 0.4.0, 704,512) | ✅ **ACTIVE** |
| `3dfxv5d.dll` | 968,932 B (has the wedge fix) | ❌ **INERT** — unreferenced |
| `3dfxv5m.sys` | 200,728 B | ❌ **INERT** — no such service |

Game-local `opengl32.dll`/`3dfxogl.dll` in `C:\Games\Quake2` **shadow system32**
and were still 0.4.0 after the system32 deploy — so the first post-deploy runs
silently measured the *old* ICD while reporting success. They were updated to
0.5.0 to match. This is the trap `CLAUDE.md` warns about and it bit immediately.

Rebooted cleanly (~150 s, `NORMAL MODE`, `NOEXECUTE=OPTIN FASTDETECT`, no safe-mode
fallback, no bugcheck).

## 3. Results — the user-mode stack is a clear win

Quake 2 timedemo, `demo1.dm2`, 640×480×16:

| Stack | fps | spread |
|---|---|---|
| **Before** (retail glide3x + ICD 0.4.0, mixed) | 159.5 | ±1.7 % (n=4), occasional MS-GL fallback |
| **After** (ours: glide2x/glide3x + ICD 0.5.0), vsync off | **172.8** | **±0.2 %** (n=4) — `172.5 / 172.8 / 173.3 / 172.6` |
| After, vsync on (default) | 60.0 | pinned to refresh — `60.1 / 60.0 / 60.0 / 60.0 / 60.0` |

**+8.3 % and an order of magnitude more consistent.** No Microsoft-GL fallbacks
occurred post-deploy; before the deploy they appeared in roughly 1 run in 5.

The 60.0 figure is **not a regression** — our `glide3x` ships
`FX_GLIDE_SWAPINTERVAL=1` (vsync on) by default, which is a deliberate invariant
asserted in `test_source_invariants.sh` to stop 200 fps tearing. Any comparison
against a retail Glide, which defaults vsync off, must set
`FX_GLIDE_SWAPINTERVAL=0` or it measures the refresh rate rather than the driver.

## 4. What remains, and why it was not done

Getting this repo's **kernel** driver onto `.143` requires a real INF/PnP
installation (the `3dfxvs2k.inf` route: service registration, `InstalledDisplayDrivers`,
PnP rebind) — not a file copy. That is a materially riskier operation than
anything done here: it can leave the box without a display, and the last time
driver work went wrong on a V5 (`.133`, 2026-08-13) the machine ended up
Safe-Mode-only with a cause never found, and was reimaged. `.143` is currently the
only live Voodoo 5.

So it is **deliberately not attempted without an explicit decision**. If it goes
ahead, the safe shape is: keep the AmigaMerlin driver installed and rolled-back-to
via Device Manager, install ours alongside, and have physical access available.

The inert `3dfxv5d.dll`/`3dfxv5m.sys` were left in place — they are harmless
(nothing loads them) and are what the INF would bind to.

---

## 5. UPDATE — this repo's kernel driver is now LIVE on `.143`

Authorised and done. **The binding turned out to be registry-only, so no INF/PnP
install was needed** — which is far safer and fully reversible.

On XPDM the display driver is bound by two things, not by filename:

```
Services\3dfxvs\ImagePath                       = system32\DRIVERS\3dfxv5r.sys
Services\3dfxvs\Device0..Device3\InstalledDisplayDrivers = 3dfxv5r      (REG_MULTI_SZ)
```

AmigaMerlin's pair is `3dfxv5r.sys` + `3dfxv5r.dll`. Repointing those five values
at `3dfxv5m.sys` / `3dfxv5d` switches the whole stack, with no driver-store
surgery, no `oem*.inf` churn, and no PnP rebind.

**Safety net built first:** full binary backup of all six files; `reg export` of
the display class key (83,234 B) and the entire `3dfxvs` service tree (340,766 B),
both pulled to the host; and a one-command rollback staged **on the box** at
`C:\RESTORE_AMIGAMERLIN.bat`, which restores all five values and runs from Safe
Mode. (XP's `reg.exe` rejects `/y` on `export` — that cost one attempt.)

### Result: it works, and it is at parity

```
InstalledDisplayDrivers = 3dfxv5d.dll          <- ours
PathName  = C:\WINDOWS\system32\DRIVERS\3dfxv5m.sys   State = Running
RLogSeq   = 588                                <- OUR flight recorder is ticking
```

Booted NORMAL mode in ~141 s, display 1024×768×32 @100 Hz, uptime climbing
(114 s → 181 s) so no reboot loop. `RLogSeq` is the decisive proof of identity:
the registry ring recorder is this repo's instrumentation and AmigaMerlin's driver
has nothing like it. (`DriverDesc` still reads "AMIGAMERLIN 3.1-R11" — that string
is cosmetic metadata in the class key, not the binding.)

Quake 2 timedemo, 640×480×16, `FX_GLIDE_SWAPINTERVAL=0`:

| Kernel display driver | fps (warm) |
|---|---|
| AmigaMerlin 3.1-R11 | 172.8 |
| **This repo's `3dfxv5d`** | **171.8** — `172.0 / 170.2 / 172.2 / 172.7` |

**Parity within 0.6 %**, i.e. inside run-to-run noise. The first run of each set is
cold (155.6 here) and should be discarded, as always on this box.

Flight recorder after the benchmark run: clean `DrvEnableSurface` /
`DrvDisableSurface` / `DrvAssertMode` lifecycle, Glide `HWCEXT` exclusive-mode
escapes, `PRIMARY-TILED` mode changes — and **no `WEDGE`, `STALL`, `DP2-*-ERR`, or
`ALLOC-FAIL` entries anywhere in the 32-slot ring**.

### What this buys

Performance is a wash, so the win is not speed — it is **ownership**: the box now
runs a stack that is entirely ours, source-available, instrumented (the ring
recorder above), and carrying the `RETRO_WEDGE_BREAK_SPINS` fix that keeps every
accelerator spin inside Windows' ~30 s video watchdog. AmigaMerlin gave the same
frames with none of that visibility and no way to fix a bug.

`.143` is now compliant with `CLAUDE.md`'s rule that the V5 box runs this repo's
drivers only — for the first time.

**To revert at any point:** run `C:\RESTORE_AMIGAMERLIN.bat` and reboot. Both
AmigaMerlin binaries (`3dfxv5r.sys`, `3dfxv5r.dll`) remain untouched on disk.
